### 3.1 NGUYÊN TẮC "LUÔN CÓ CÂU TRẢ LỜI"

Không được có trường hợp user gửi message hợp lệ rồi chatbot im lặng.

Mọi request phải kết thúc ở một trong:
1. câu trả lời intent cụ thể;
2. kết quả tra cứu động;
3. câu hỏi làm rõ;
4. fallback có gợi ý;
5. safety/unsupported response.

Không được bịa câu trả lời để đạt mục tiêu "mọi khả năng".

"Mọi khả năng" trong task này nghĩa là:
- mọi chức năng/route/user journey đang có trong dự án đều phải có coverage;
- mọi câu hỏi ngoài catalog phải có fallback hữu ích;
- mọi entity search hợp lệ phải có kết quả hoặc thông báo không tìm thấy;
- không được suy đoán dữ liệu không tồn tại.

### 3.2 DỮ LIỆU ĐỘNG VỀ SẢN PHẨM / DỊCH VỤ / COACH

Sản phẩm:
- intent có thể tra cứu Product theo từ khóa bằng API search hiện hữu;
- nếu API hỗ trợ filter/sort thì reuse đúng contract;
- không tự invent giá, tồn kho, giảm giá;
- khi có dữ liệu, trả tối đa 3–5 kết quả để UI không quá dài;
- mỗi kết quả có action mở Product detail.

Coach:
- intent có thể tra cứu Coach theo tên/chuyên môn/thông tin public mà API hiện hữu cho phép;
- có thể trả availability chỉ khi user đã chỉ rõ Coach/ngày và API read-only hiện hữu hỗ trợ;
- không nói slot còn trống nếu chưa đọc authoritative availability;
- không tự đặt lịch.

Dịch vụ:
- Membership, booking Coach, workout, Seller, Marketplace, Admin được mô tả theo contract thật;
- nếu hỏi "dịch vụ nào có trên GYMFIT?" chatbot phải có response tổng hợp theo role và public features hiện tồn tại.

Cửa hàng:
- nếu public Shop API hiện hữu, có thể search read-only;
- nếu không, chỉ hướng dẫn route Shop/Product.

Đơn hàng / lịch hẹn / workout của user:
- chỉ đọc dữ liệu của chính user từ API đã được backend scope;
- không dùng userId do client tự nhập để truy cập user khác;
- nếu role không phù hợp, không gọi adapter.

### 3.3 ENTITY PARSING

Tạo deterministic parser cho các kiểu truy vấn phổ biến, ví dụ:

- `tìm whey`
- `tìm sản phẩm whey`
- `whey dưới 500k`
- `sản phẩm từ 300k đến 700k`
- `coach online`
- `coach tên an`
- `coach nào còn lịch ngày 12/08`
- `gói pro có gì`
- `đơn hàng của tôi`
- `lịch hẹn coach của tôi`

Parser có thể nhận:
- query text;
- category;
- minPrice;
- maxPrice;
- sort;
- date;
- mode;
- entity name;
- route context.

Chỉ dùng filter mà API hiện hữu hỗ trợ.
Nếu parser nhận được điều kiện API không hỗ trợ:
- không giả kết quả;
- dùng điều kiện có thể xác minh;
- giải thích ngắn phần chưa lọc được.

### 3.4 RESPONSE DELAY / "ĐANG SOẠN"

Chatbot phải có response delay ngẫu nhiên nhỏ để hội thoại tự nhiên.

Đây là delay UX, KHÔNG phải mô phỏng hay tuyên bố "AI đang suy nghĩ".

UI text hợp lệ:
- `Đang soạn...`
- `Đang tìm thông tin...`

Không dùng:
- `AI đang suy nghĩ`
- `Mô hình đang suy luận`
- `Đang phân tích bằng AI`

Delay gợi ý:
- static reply: khoảng 350–1100 ms;
- reply dài: có thể cộng thêm theo độ dài, tổng tối đa khoảng 1600 ms;
- dynamic read-only lookup: hiển thị loading cho tới khi request xong, sau đó thêm tối đa 150–500 ms để tránh nhấp nháy;
- không cố ý delay quá 2 giây.

Delay phải:
- cancel khi widget đóng/unmount;
- không block UI thread;
- dùng setTimeout/Promise;
- test được bằng injectable delay/random provider hoặc fake timers;
- production random được phép, test phải deterministic.

## 4. RULE ENGINE

Không dùng giant if/else.

Mỗi intent typed tối thiểu:
- id
- category
- priority
- roles?
- exactPhrases?
- phraseBoosts?
- keywordsAny?
- keywordsAll?
- negativeKeywords?
- minScore?
- responses
- suggestions?
- actions?

Normalization:
1. Unicode NFC.
2. lowercase.
3. trim/collapse whitespace.
4. normalize punctuation.
5. giữ original message.
6. tạo bản accent-insensitive chỉ để matching: NFD, bỏ combining marks, map đ→d.
7. không sửa original text.

Scoring phải deterministic và test được. Gợi ý:
- exact phrase +12
- phrase boost +6
- keywordsAll full +8
- keywordAny +2/token
- route/context +2
- previous intent +1/+2
- negative keyword -8
- role mismatch = block intent

Nếu score thấp → fallback. Nếu top1/top2 quá gần → clarification. Không đoán bừa. Nội dung response không được random theo kiểu thay đổi ý nghĩa. Nếu một intent có nhiều cách diễn đạt tương đương, có thể dùng stable hash để chọn deterministic.
CHỈ response delay được random trong production theo mục 3.4.

Engine phải hỗ trợ reply type:
- STATIC
- DYNAMIC_LOOKUP
- CLARIFICATION
- FALLBACK
- SAFETY

Dynamic lookup intent phải khai báo adapter id + entity parser contract, không gọi network tùy tiện.

Reply contract tối thiểu:
- intentId
- score/confidence
- replyType
- message
- suggestions
- actions
- results? (danh sách entity read-only)
- sourceState? (`STATIC`, `LIVE_DATA`, `NOT_FOUND`, `UNAVAILABLE`)

- suggestion cards/chips theo role.

Sau mỗi câu trả lời:
- nếu có next actions, hiện 2–5 quick replies;
- user vẫn có thể bỏ qua suggestions và gõ tự do.

Response delay:
- static reply có randomized UX delay theo mục 3.4;
- dynamic reply dùng actual request loading + bounded polish delay;
- không giả là AI reasoning.

Persistence:
- sessionStorage;
- max 40 messages;
- versioned key;
- corrupted JSON fallback;
- không lưu password/token.

Input:
- max 500 chars;
- empty ignored;
- Enter send;
- xử lý IME/composition để gõ tiếng Việt không gửi sớm;
- user có thể gửi message tiếp sau khi bot hoàn tất;
- trong lúc bot đang xử lý, không tạo double-send race.

Không dangerouslySetInnerHTML, không eval, không arbitrary URL, không dynamic HTML.

Dynamic entity results:
- Product/Coach/Shop result hiển thị dạng compact cards;
- max 3–5 result/reply;
- có `Xem chi tiết`;
- không render dữ liệu ngoài fields đã typed/sanitized;
- nếu 0 result: câu trả lời `Không tìm thấy...` + gợi ý đổi từ khóa;
- nếu API error: nói `Hiện chưa tải được dữ liệu` + link đến trang search nếu có.
